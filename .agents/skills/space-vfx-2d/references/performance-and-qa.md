## 0. 最重要的一条：什么能自动验证，什么不能

**必须先把这条说清楚，否则后面所有数字都可能变成编造的。**

### 能在 node 下自动验证（`npm run check`）

- **物理未被触碰**：跑 N 步 `stepGame` + `updateVisuals`，与不跑 `updateVisuals` 的对照 `expect(a).toEqual(b)`。
- **绘制调用数**：测试里用**录制型 mock `CanvasRenderingContext2D`**，把 `arc` / `rect` / `fill` / `stroke` / `setLineDash` 等操作记下来，断言次数与几何。`tests/render-visuals.test.ts` 已经在用这个模式。
- **几何契约**：基础星光形变的边界 / 中心连续性、位移上限、小行星轮廓不超出半径；粒子相关历史断言仅用于适合的天体效果。
- **确定性**：同 seed 两次生成逐位相同。
- **帧率无关**：30 / 60 / 144 三种调用节奏下，尾迹顶点与粒子状态一致（**只在直线路径上断言逐位相等**，曲线路径用长度/数量的容差断言——逐位相等会 flaky）。
- **node 安全性**：在测试文件顶部 import 所有渲染模块。任何模块顶层碰 `document` / `window` / `getContext` 都会在 import 时抛错并让整个文件失败。**import 本身就是这条的测试**，不要写静态扫源码的测试。

### 只能在真实浏览器里验证（人工）

- 好不好看、挡不挡视线、氛围对不对。
- **实际 FPS 与帧时间**。
- Console 报错与 WebGL/Canvas 警告。
- 长时间运行的显存/堆增长。

### 关于"我跑不了浏览器"这件事

本环境**没有安装任何浏览器自动化**（`package.json` 里没有 playwright / puppeteer，`npm run check` 也只有 `test` + `build`）。

> **如果你（Codex/Astra）无法启动真实浏览器，必须明确说出"我无法验证视觉效果"，并只提交 node 侧可验证的证据。**
> **绝不允许**：编造截图、编造 FPS 数字、把"应该没问题"写成"已验证"、用 `npm run build` 通过冒充视觉验收通过。

无法验证时，交付里必须有一节写明：哪些已自动验证（附测试名）、哪些**未验证**（附具体待人工确认项）。

## 1. 性能预算（目标值，必须实测确认）

目标分辨率 **1920 × 1080**、`devicePixelRatio ≤ 2`、一般桌面浏览器、60 FPS。

| 指标 | 目标 | 硬上限 |
| --- | --- | --- |
| 整帧时间 | ≤ 10.0 ms | 16.7 ms（60 FPS） |
| 其中渲染（`render()` 全程） | ≤ 6.0 ms | 9.0 ms |
| 其中 VFX 部分（粒子 + 星云 + 明暗） | ≤ 2.5 ms | 4.0 ms |
| 粒子状态更新（CPU，1000 粒子 / 4 源） | ≤ 1.5 ms | 2.5 ms |
| 绘制调用 / 帧（medium） | ≤ 130 | 180 |
| 运行 10 分钟后 JS 堆增长 | ≤ 5 MB | 12 MB |
| 粒子存活数 | 恒 ≤ 池容量 | —— |
| 星云块缓存条目 | 恒 ≤ 24 | 32 |

> 这些是**假设性目标**，不是实测值。第一次跑完真实浏览器测量后，**以实测为准回填本文档**，并把实测数字写进 `README.md`。如果实测指向别处，不要为了凑表格去改实现——改表格。
>
> **已回填（2026-10-16）**：绘制调用与帧时间两行已换成实测；其余各行（10 分钟堆增长、星云缓存条目）**仍未测**，别当成已验证。
> 绘制调用实测：`off` 31 / `low` 60 / `medium` **64** / `high` 71（含全部 canvas 绘制调用）。目标 ≤ 130、硬上限 180，**实测远在预算内**。
> 帧时间实测（无头 Edge，1440×900，DPR 1，240 帧）：`?fx=off` p50 16.7 / p95 22.6 / max 25.3 ms；`?fx=medium` p50 16.8 / p95 23.0 / max 25.9 ms。p50 两者都钉在 60 Hz 的 16.7 ms 上。**这组数字是删掉场粒子之前量的**（当时 medium 还有那 8 次 `stroke`）；删掉之后没有重测帧时间，因为调用数已经少了 8、方向只会更好——别把这句读成"删除提升了帧时间"，那没测过。
> **注意最早那版估计表高估了每一档**（`medium` 估 ~86，实测 56），也高估了档间距。估计值系统性偏高，因为批量声明是真的：真正随数量增长的量一个都没有。

### 绘制调用预算（medium 档，单场景，实测）

**下表是删掉场粒子之后的数字。** 同一套量法在删除前量到 `off` 31 / `low` 60 / `medium` 64 / `high` 71，删除后 `off` 31 / `low` 52 / `medium` 56 / `high` 63——每档正好少 8，就是粒子那一趟的 8 次 `stroke`（2 池 × 4 亮度桶），而 `off` 一次没变（该档粒子池容量为 0）。

| 来源 | 调用数 | 顶点 | 说明 |
| --- | --- | --- | --- |
| 星空 | 9 | 800 / 2220 / 4884 | 3 层 × 3 亮度桶，**调用数与星数无关**；顶点数**不**恒定，随 zoom 变化（依次为 `low` / `medium` / `high` 实测） |
| 星云 | 5–14 | 各 1 | 每团一次 fill（渐变缓存），`nebulaBlobs` 门控 |
| 节点辉光 | 12 | 各 1 | 每节点 3 层加法光晕 + 2 圆盘 + 白热核心 |
| 尾迹 | 5 / 条 | 各 13–14 | 5 个收细分桶；本场只有 1 条飞船尾迹 |
| 天体 | 8 | 各 1–4 | 随实体数增长（既有行为） |
| 预测虚线 | 1 | 121 | |
| HUD / 小地图 | 11 | 0 | 2 `fillRect` + 7 `fillText` + 2 `strokeRect`，既有 |
| **合计** | **56**（11 是 HUD，45 是路径绘制） | | |

**由构造方式保证有界**：星空恒 9 次、节点辉光恒 12 次、尾迹恒 5 次/条，都与元素数量无关。只有天体循环随实体数增长，而它今天就已经在增长。

> **一个容易写错的推论**：星空"9 次调用"是恒定的，但**一帧画出的 `rect` 顶点数不是**——星点归一化存在一个 tile 里，tile 会在视口内**平铺重复**（`firstI..lastI` / `firstJ..lastJ`），所以顶点数 = 星数 × 覆盖视口所需的重复数，随 zoom 与每层 `tileScale` 变化（`low` 800 / `medium` 2220 / `high` 4884，同为 `medium` 的不同运行也量到过 2102）。引用"星空很便宜"时引**调用数**，不要引顶点数，更不要把顶点数除以星数得出"每颗星几个顶点"之类的结论。

## 2. 质量档位

既有 `QUALITY` 表（`src/render/scene-visuals.ts`）扩展为：

```ts
export interface QualitySpec {
  stars: number;
  trailPoints: number;
  fieldRings: number;        // 仅 debug 叠层使用
  streamlines: boolean;      // 仅 high（可选特性）
  particles: number;         // 合适的天体粒子容量；正式引力场粒子固定为 0
  nebulaBlobs: number;       // 0 = 关闭星云
  warp: boolean;             // 总门控：星空形变 + 明暗褶皱 + 事件扰动
  celestialDetail: number;   // 0–1，日珥 / 吸积盘粒子的缩放系数
}
```

| 档 | `?fx=` | stars | trailPoints | particles | nebulaBlobs | warp | celestialDetail |
| --- | --- | --- | --- | --- | --- | --- | --- |
| off | `off` | 0 | 0 | 0 | 0 | false | 0 |
| low | `low` | 180 | 32 | 160 | 0 | false | 0.4 |
| medium（默认） | `medium` | 500 | 64 | 320 | 6 | true | 1.0 |
| high | `high` | 1100 | 96 | 640 | 14 | true | 1.6 |

### 明暗扰动的质量门控（新增规范，尚未实装）

保留上述字段与数字兼容性，`particles` 不再意味着恢复场粒子。渲染侧可选扩展 / 配置建议：

| 档位 | starWarp | luminanceRipple | interactionRipple | idleRipple | 最大明暗控制点 | 最大事件 |
| --- | --- | --- | --- | --- | --- | --- |
| off | false | false | false | false | 0 | 0 |
| low | false | false | false | false | 0 | 0 |
| medium | true | true | true | false | 64 | 4 |
| high | true | true | true | false（试玩可开） | 96 | 4 |

全部受 `warp` 总门控；`fx=off` 的旧画面与只读物理契约优先。独立调试开关和全部参数的唯一规范见 `gravity-field-vfx.md` §9.5。不要复制多套默认值到不同文档或把建议字段当成当前接口。

新增成本按 **星点数×可见场 / 事件数 + 明暗控制点数×可见场 / 事件数** 估算，不能继续宣称“每星每节点约 8 次运算”。sqrt / exp / tanh 和采样均需 profile；时间衰减与事件常量每帧预计算一次，空间项按点计算。原 56 次绘制是历史场景，不是新效果测量；medium 最多增加 64 次印章 drawImage，目标仍按总调用预算与实测帧时判断。缓存核条目固定为明 / 暗两张，可选变体需设小上限；事件最多 4、源快照按既有场收集上限加消退槽位定容，网格最多 64/96，质量切换不能泄漏旧缓存。

### 铁律

1. **不同档位不得改变实际游戏物理结果。** 唯一允许改变的是画面。
2. **`off` 必须与"加特效之前"逐像素一致。** 它是 A/B 基线，也是出问题时的二分定位工具。粒子容量 0、星云 0、`warp: false`，走的是旧分支。
3. 档位选择走 `parseQuality(search)`，读 URL 的 `?fx=`。**不放进 `debug/config.ts`**——那个文件是 DEV 门控的，而 `?fx=` 应当在生产构建里也生效，且不该改关卡配置。

## 3. Canvas 2D 优化清单与取舍

| 技术 | 什么时候用 | 代价 / 什么时候别用 |
| --- | --- | --- |
| **Radial Gradient** | 天体盘面、节点光晕、星云团；空间褶皱可用缓存软印章 | 创建有成本 → **必须缓存**（按 kind + 量化半径，坐标建在原点）。绝不每帧 `createRadialGradient` |
| **Alpha Compositing** | 身份色、HUD、合成后明暗褶皱 | 玩家节点尾迹必须用它；明暗先求和再画一个符号通道，globalAlpha 随共享包络变化，save/restore 防泄漏 |
| **Additive（`'lighter'`）** | 粒子、光晕、星云、飞船尾迹 | 叠加过多会糊成白块 → 每层峰值 alpha 见 `art-direction.md` §3 的亮度阶梯 |
| **缓存画布 / OffscreenCanvas** | 复杂的静态内容反复重绘（例如星云团、行星环） | 在**确定性**内容上才有收益；每帧变化的内容缓存反而更贵。注意 `OffscreenCanvas` 在测试的 node 环境不可用 → 只能出现在绘制函数内部，**绝不能在模块顶层** |
| **粒子对象池** | 粒子、脉冲 | 必做。定容 SoA，死亡只标记不回收 |
| **批量绘制** | 粒子、星空 | **关键手段**。按亮度桶分组，每桶一次 `fillStyle` + 一次 `fill()` |
| **`ctx.rect` 而非 `ctx.arc`** | 所有小尺寸点状元素 | `arc` 构造贝塞尔子路径，比 `rect` 明显贵。星点与粒子一律 `rect` |
| **分层渲染** | 背景 / 世界 / 屏幕空间 | 必做，但用现有的 `save/restore` 与变换分层即可，不必引入多画布 |
| **简化光晕** | 所有光晕 | 用 2–3 层不同半径的渐变叠出层次，**不用模糊** |
| **低分辨率效果层再合成** | 昂贵的全屏效果 | **本作不推荐**：会引入可见的像素化，且与"克制"取向冲突。除非实测逼近硬上限，否则不做 |
| **`shadowBlur`** | **永不使用** | 昂贵且偏霓虹，与本品气质相反 |
| **`ctx.filter`** | **永不使用** | 每次都触发一次离屏合成，代价远超收益 |

### 热点排序（优化时按这个顺序找）

1. 每帧 `createRadialGradient` / `createLinearGradient`
2. 逐元素 `beginPath()` + `fill()` / `stroke()`
3. 逐元素 `fillStyle` 字符串拼接
4. 粒子更新循环里的对象分配（`{x,y}` 字面量、`.filter()`、展开运算符）
5. 屏幕外内容仍被绘制

## 4. 浏览器视觉验收流程

### 4.1 步骤

1. `npm run dev`（脚本已是 `vite --host 127.0.0.1`）。
2. 打开 **DevTools 的 Console**，确认**无报错、无警告**。有报错就停下修，不要继续。
3. 打开 **Performance** 面板，录制 10 秒典型操作，记录：
   - 平均帧时间 / FPS
   - 最长帧（jank）
   - `render()` 在火焰图里的占比
4. 依次用四个档位跑同一段操作，截图对比：`?fx=off` / `?fx=low` / `?fx=medium` / `?fx=high`。
5. 切到标签页 10 秒再切回，确认**没有一次性跳变**（`MAX_FRAME_SECONDS = 0.1` 的钳位应当已经兜住）。
6. 拖拽改变窗口大小，确认 `ResizeObserver` 路径（`main.ts` 的 `resize()`）不出错、星空不突现。

### 4.2 建议加的机器可读钩子

`main.ts` 已经在往 `canvas.dataset` 写 `phase` / `fields` / `scene` / `zoom` / `prediction`。按同样的方式补上，让人（或将来接了自动化的代理）能直接读到数字：

```ts
canvas.dataset.fx = visuals.quality;
canvas.dataset.frameMs = frameMs.toFixed(2);      // 最近一帧的耗时
canvas.dataset.particles = String(liveParticles);
```

**注意**：写 `dataset` 也是 DOM 操作，**只能在 `main.ts` 里做**，绝不能在 `src/render/*` 的模块顶层。

## 5. 十个典型测试场景

每个场景都要记录：**帧时间、绘制调用数、肉眼观察结论**。off 的门控与基线图像验收另按 §7.6 执行，不能仅凭混合模式判断。

| # | 场景 | 怎么到 | 看什么 | 通过标准 |
| --- | --- | --- | --- | --- |
| 1 | 普通飞行 | 默认关卡，不做任何操作地飞 | 基础帧率；星空视差是否自然 | 整帧 ≤ 10 ms；无突现 |
| 2 | 蓝球单独施力 | 只按 P1 的 `[F]` | 星空压缩、背景压暗、褶皱稳定 | 基础位移向内，无常驻流动粒子 / 循环启动动画 |
| 3 | 金球单独施力 | 只按 P2 的 `[Enter]` | 星空扩张、局部微亮、短暂柔波 | 基础位移向外，无雷达扫描环 |
| 4 | **双场同时施力** | 两个键都按 | **重叠区基础星点位移及合成明暗** | 与 `?dev=1` 的合力箭头方向一致；两场相反处能看出抵消 |
| 5 | 多个天体同时受力 | `?dev=1&scene=coop_test`（`developmentRegistry`） | 天体被推动时视觉位置是否跟随；帧时间 | 视觉位置 = `body.position`；大质量下仍 ≤ 10 ms |
| 6 | 太阳 / 黑洞在画面中 | **当前两关没有 `star` / `black_hole` 实例**，需在 `src/debug/` 造临时场景 | 是否被白色光晕淹没；吞噬盘是否被覆盖 | 画面不被淹没；`captureRadius` 区域完全干净 |
| 7 | 摄像机高速移动 | 让飞船全速朝一个方向飞 | **拖尾不能反向**（见 `gravity-field-vfx.md` §8.2） | 尾巴在飞船之后，不甩向相反方向 |
| 8 | 大地图远距离探索 | 持续飞出 `mapBounds` | 星空是否跑空；星云区块是否闪烁 | 星空永不空；同一区块两次经过**完全一致** |
| 9 | 窗口大小变化 | 反复拖拽窗口 | 星空密度是否恒定；有无报错 | 密度不变（tile 随视口推导）；Console 干净 |

**场景 5 的已知性能悬崖**：`physics/world.ts` 的 `INDEX_THRESHOLD = 48`，天体数超过 48 时空间索引接管。测大质量场景时注意跨过这个阈值前后的差异——那是**既有**行为，不是本次改动引入的。

### 5.1 新增空间扰动验收矩阵（必须实际试玩，当前均待实现后验证）

每项记录同 seed / 机位 / 输入、fx 档位、独立开关、配置、视频片段（静态截图不足以证明衰减）、帧时 p50/p95、绘制调用与肉眼结论。至少覆盖：

| 场景 | 操作与观察 | 通过标准 |
| --- | --- | --- |
| 蓝球静止开启 | 开启后保持节点不动至少 8 s | 星光向内压缩、局部变暗，启动扰动消退；稳态安静，无循环缩放光圈 |
| 蓝球快速移动 | 开启后快速平移并停下 | 柔和拖拽 / 剪切，世界运动触发波；停下后平滑衰减，无颗粒汇聚 |
| 金球静止开启 | 单独开启并保持不动 | 星光向外扩散、局部微亮，亮度受限且不盖过飞船 |
| 金球快速移动 | 开启并快速移位 | 短暂外扩扰动与星点微移同步，发出的波留在触发世界原点，无扫描圆环 |
| 两场重叠 | 同向增强、反向抵消、移动过合力零点；交换采样遍历顺序 | 稳态基础位移与真实合力同向；抵消连续，无零点翻跳；明暗先合成受限，不随事件 / 源叠加越来越亮 |
| 场突然关闭 | 在波峰及快速移动时关闭，再重开 | 基础位移与明暗连续恢复，残余波自然衰减；无单帧撤盘 / 反向闪光 / 重播积压 |
| 摄像机高速移动 | 节点稳定，镜头平移 / 缩放，跨 tile；DPR 1 / 2，极小 zoom | 相对当前相机投影无额外漂移 / 闪烁；不触发移动事件；无漏星 / 重复星 / 重复缩放 |
| 关闭高级特效 | 相同初始状态、输入、dt 对比 off / low / high | 物理、碰撞、轨迹、场景结果逐位相同；off 新增绘制与采样均为零，像素基线一致 |
| 独立关明暗 | luminanceRipple=false，保留星点和 interaction | 仅明暗通道消失；星点仍按同一事件变化，物理不变 |
| 独立关事件 | interactionRipple=false，保留基底 | 两通道均无事件项；静态形变与明暗保留，恢复开关无积压事件 |
| 低帧率 / 暂停 / 换场景 | 30/60/144 Hz 视觉更新，暂停恢复，checkpoint / revision 重置 | 连续包络在等年龄处一致；触发时刻误差≤一个视觉步；暂停冻结，换场景池 / 前值清空 |
| 事件池满 / 长时间运行 | 连续移动与开关 10 min | 满池不硬删旧波、不扩容；停止后事件归零；内存与帧时符合预算 |

**视觉不合格**：看起来只是几个呼吸光圈、能清楚追踪闭合同心圆边界、雷达扫描环、明暗波与星点不同步、持续向中心 / 外围流动的场粒子、或遮蔽关键对象。自动测试不能替玩家判定这些问题。

## 6. 截图要求

- 每个档位至少 **4 张**：`off` / `low` / `medium` / `high`，**同一机位、同一时刻**（暂停后截图，避免飞船位置漂移）。
- 至少覆盖三种构图：
  1. 飞船 + 两个场重叠
  2. 黑洞（或太阳）在画面内
  3. 空间站 + 目标标记 + 小地图同框
- 命名：`fx-<档位>-<场景>.png`，例如 `fx-high-overlap.png`。
- **必须真实截取。** 不得用示意图、手绘、或从别处复制的图冒充。

## 7. 物理与视觉一致性检查（**最重要的一组**）

### 7.1 开关特效后物理逐位相同

```
同一初始 state + 同一输入序列 + 同一 dt 序列
  ├─ A 组：只跑 stepGame
  └─ B 组：每步之后额外跑 updateVisuals
断言 A === B（逐位）
```

这是**可以在 node 下自动化**的最强断言：它把"VFX 只读"从一个承诺变成一条可证伪的事实。`updateVisuals` 刻意不接收 `Camera`、不接收 `ctx`，就是为了让这条成立。

再用 `fx=off` 与 `fx=high` 各跑一遍真实浏览器里的同一段操作，确认**输入相同 ⇒ 轨迹相同**。

### 7.2 场的视觉与物理阈值对齐

- 用 `?dev=1` 打开等高线，确认**边界环精确落在 `field.radius`**——那正是 `fieldAcceleration` 停止返回零的距离（`fields.ts` 的 `distance >= field.radius`）。
- 对照开发面板里飞船的 `|a|`：越过边界环的一刻应当归零。

### 7.3 空间形变与统一扰动的自动验证

- 对同一固定点，复用真实采样器求 `A`，稳定状态下 `D_base` 与其同向；等强反向场抵消，随机交换源顺序误差≤浮点容差。不要拿事件波的瞬时方向冒充真实合力。
- 在每源中心、`R-ε / R / R+ε`、两场合力零点做双侧采样：值有限、位移连续趋零 / 穿零，检查递减 ε 的差值收敛，不只断言单一截图。`R` 处真实场为零，不能拿边界值作为非零强度归一化分母。
- 覆盖不等强度、强度突变、极性翻转、关闭 / 重开：总位移≤配置上限，明暗≤正负上限；视觉快照消退期间与即时合力有区别，调试箭头继续读实时 GameState。
- 固定 seed、事件原点、年龄，在星点 / 明暗控制点的**同一世界采样位置**比较共享 `H`；改变事件年龄 / 幅度时两通道同时变化。独立关闭 luminance 不改变位移，关闭 interaction 两通道都去掉事件项。
- 单独改变相机（含 zoom 与 DPR）：世界事件原点 / 年龄 / 触发计数不变；通过 `screenToWorld(camera,s0)` 得到一致采样，屏幕输出只含当前投影与受限偏移，不累计历史屏幕坐标。
- 同事件在 30 / 60 / 144 Hz 等年龄处验证解析包络（允许浮点容差），触发阈值量化≤一个更新步，不要求不同事件检测帧率下所有状态逐位相等。物理 A/B 仍逐位比较。
- 在 `life` 结束前后检查幅度与一阶变化趋零；满池不替换可见事件、源关闭不立刻清快照，零容量 / 零幅度安全旁路。
- 录制型 Canvas mock 断言 off 无任何新采样 / 印章 drawImage / 加法混合；单独“没有 lighter”不足以覆盖 source-over 明暗。按 §7.6 验证明确门控与确定性 off 图像基线，状态 save/restore 无 alpha / transform 泄漏。

**Deprecated / Rejected Experiment**：原粒子方向实验曾记录径向速度 −28.2、四池手性 1.0、重叠方向检查通过，仍被玩家否决。只保留为“数值正确不等于视觉有效”的记录；不作为新效果验收目标，也不再以“相邻两帧没有新信息”禁止安静的氛围变化。

---

### 7.4 视觉不超出碰撞边界

- 开船撞小行星：碰撞应发生在**可见边缘处或更早**，绝不更晚。
- 行星环若画到 `body.radius` 之外，必须有对应的碰撞半径设置（见 `celestial-effects.md` §2.3）。
- 黑洞吞噬盘尺寸**不得**改变。

### 7.5 HUD 遮挡检查

- 四个档位各跑一遍，确认 **HUD 面板不遮挡飞船、不遮挡危险天体轮廓、不遮挡目标标记**。
- 检查左上角状态文字区域**没有暗角**（本 Skill 明确不做暗角）。
- 小地图面板的边框宽度不应因特效改动而变化（注意 `celestial.ts` 里既有的 `3/zoom` lineWidth 泄漏，那是**故意保留**的）。

### 7.6 `fx=off` 的特效门控与确定性基线图像

以下是后续实现必须具备的验收规范；本次文档修订不向游戏添加测试或宣称图像验收已执行。

1. **明确门控测试**：在实际更新 / 绘制入口使用调用 spy、计数器或录制型 Canvas mock，逐项检查星点形变、明暗（含 `source-over` 暗化）、交互事件、idle、节点光晕、尾迹、星云与天体新增特效。`fx=off` 时应走旧渲染路径，新增采样、事件生成 / 推进、新缓存初始化及新增特效绘制调用均为零；不能只检查 shape 名称或 `lighter`。单项开关关闭也须旁路对应通道。
2. **正向对照与残留状态**：同一可见场景先启用待测效果，确认 spy / 计数器确实能观测其调用，再关闭并断言相应调用为零。覆盖全新 VisualState、先 high 运行后切 off（缓存与余波已存在）、以及 `fx=off` 同时附带单项强制开启的调试覆盖；off 始终优先，缓存和消退快照不能漏画。明暗关闭后星点仍可按门控运行，反之亦然，不改变真实物理结果。
3. **确定性图像对比**：保存改动前的旧路径 / off 基线，并与改动后的 off 输出比较。两次在同一运行环境中执行，固定浏览器版本、操作系统 / 字体、渲染后端、Canvas CSS 尺寸、DPR、相机、相同初始 GameState、确定性随机 seed、输入序列、dt 序列及捕获时刻；重置视觉状态并等待必要资源就绪。图像需与来源提交和这些条件一起记录，不能拿不同环境的旧截图直接下结论。
4. **通过判据**：对同一条件、同一帧的 Canvas 像素比较，要求尺寸一致、差异像素数为 0；另覆盖 high→off 后同一物理状态的帧，验证旧余效已全部旁路。若环境本身不稳定，先固定环境再重测，不能静默放宽阈值、掩盖差异或用新输出自动覆盖旧基线。门控测试证明代码旁路，图像对比证明最终画面；两者都要通过。

`globalCompositeOperation === 'lighter'` 的缺失仅为辅助断言，**不能证明全部特效已关闭**。尤其 `source-over` 暗化可以在没有任何加色混合时改变画面，必须同时满足明确门控与图像基线要求；无法执行时如实记录待验收。

## 8. 性能回归与故障排查

### 二分定位

1. `?fx=off` —— 若此时仍有问题，说明**不是特效层**的问题，去查别的。
2. 逐项关闭：依次禁用 `idleRipple` → `interactionRipple` → `luminanceRipple` → `starWarp` → `warp`，再查天体 `particles` / `nebulaBlobs` / `stars`，看哪一项触发问题。
3. 若只在 `high` 出现，检查明暗网格点数、星点顶点数、天体粒子及其他档位项；不要假设调用数能代表所有 CPU 成本。
4. **若某个特性在 profile 里显形，就砍掉它。** 本 Skill 明确接受"砍特性"作为合法结论——基础星空形变优先保留；等高线环继续仅用于 debug，不能以砍特性为由把它恢复为正式画面。

### 常见症状表

| 症状 | 先怀疑 | 处理 |
| --- | --- | --- |
| 粒子数只增不减 | 池的回收分支没走到 / `live` 高水位没降 | 检查死亡标记与 `live` 收敛 |
| 高刷屏上粒子和 60 Hz 不一样 | 用了按帧的衰减（`v *= 0.98`） | 换成 `1 - exp(-k·dt)` |
| 画面糊成白块 | 加法混合层数或 alpha 超出亮度阶梯 | 按 `art-direction.md` §3 逐层压回 |
| 星空闪烁 | 每帧重新随机 / tile 尺寸随帧变 | 用 `seededRandom`，tile 只随视口尺寸变 |
| 场关闭跳变 | 立即删掉 active 场快照 / 事件到期硬截断 | 保留 release 权重、T 末尾平滑窗，过可见残差阈值再回收 |
| 波纹像雷达 | 波包过窄、描边圆环、噪声频率过低或形状太规则 | 加宽空间尺度、降对比度，用稀疏软核重建，不画轮廓线 |
| 重叠越来越亮 | 分别绘制每场 / 每事件的加色亮盘 | 先合成有符号 B，再限幅，以 source-over 一次消费 |
| 拖尾反向 | 存了屏幕坐标 | 存世界坐标 |
| 飞船难辨认 | 某层 alpha 盖过了 L9 | 按亮度阶梯下调该层 |
| 切标签页回来炸一下 | 视觉时钟未钳位 | 确认 `MAX_FRAME_SECONDS = 0.1` 仍生效 |
| `dist` 体积暴涨 | 引入了运行时依赖 | 回退；本项目零依赖 |

## 9. 最终视觉评分表

每项 0–5 分。**由人对照截图打分，不由代理自评。**

| 维度 | 0 分 | 5 分 | 得分 |
| --- | --- | --- | --- |
| **可读性** | 飞船/危险天体被特效淹没 | 任何情况下飞船与危险轮廓一眼可辨 | |
| **物理诚实性** | 视觉方向与物理矛盾 | 受力方向、抵消、硬截断全部视觉上说得通 | |
| **氛围** | 像物理演示图 | 像幽暗精密的深空 | |
| **克制** | 到处荧光、光环、粒子遮天 | 该亮的地方亮，其余安静 | |
| **一致性** | 各元素颜色/亮度各自为政 | 全部落在亮度阶梯与 token 体系内 | |
| **性能** | 掉帧明显 | 四档都稳，`off` 与基线一致 | |
| **HUD 主次** | HUD 与飞船抢注意力 | HUD 是仪器，主画面是主角 | |

**合格线：总分 ≥ 26/35，且「可读性」与「物理诚实性」都 ≥ 4 分。**

任何一项出现以下情况直接判不合格：

- 正式画面里出现引力场线 / 磁场线 / 网格作为主要表达。
- 基础星空形变方向与真实合力矛盾，或恢复已拒绝的常驻场粒子。
- 空间效果只剩静态染色盘、呼吸光圈或清晰雷达扫描环。
- 飞船在特效打开时变得难以辨认。
- 关闭特效能改变物理结果。
- 有编造的截图或性能数字。
